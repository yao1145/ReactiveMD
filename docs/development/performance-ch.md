# 性能测量

当前 0.6.1 的编译时间、内存峰值、密集段落和大量组件压力测试见 [2026-10-28 编译性能调查](compiler-performance-2026-10-28-ch.md)，附可复现脚本与浏览器 Worker 实测。

普通段落直接解析、无替换 Markdown 的解析树复用，以及优化前后的时间、内存和语义对照，见[密集段落编译优化](dense-paragraph-optimization-2026-10-28-ch.md)。

在源码仓库根目录构建语言包，然后运行：

```sh
npm run build
npm run benchmark
```

脚本对每个场景预热 3 次、测量 20 次，报告中位数和 P95，原始结果写入 `artifacts/benchmark.json`。可用 `npm run benchmark -- --iterations 50 --output artifacts/benchmark-50.json` 改变次数和输出位置。报告包含包版本、Node 版本、操作系统和 CPU 信息。

## 本地基线

2026-10-22，Reactive MD 0.3.0，Node 22.17.0，Windows x64，Intel Core Ultra 5 125H。测量时机器上也有其他开发进程运行。该基线早于 0.4.0 发布；作为发布对比前应重新运行基准。

| 场景 | 中位数 | P95 |
| --- | ---: | ---: |
| 编译费用示例，378 字符 | 2.51 ms | 5.83 ms |
| 编译 250 行响应式表格，7,161 字符 | 17.04 ms | 28.05 ms |
| 编译 100 节文章，15,550 字符 | 45.34 ms | 59.81 ms |
| 连续 100 次状态写入与表达式求值 | 0.20 ms | 0.34 ms |
| 三条曲线，每条 200 个采样点 | 0.55 ms | 1.61 ms |

计时包含正确性断言，运行时场景的一次测量包含 100 次更新。绘图场景包含正常函数与非网格渐近线的断点检查。

这些数据测量 Node 中的编译、求值和采样，不包含浏览器排版、绘制或输入到画面的延迟。数值用于同条件下比较版本，不设置跨机器通过阈值，也不代表源码上限内的所有文档都有相同耗时。CI 保存 Node 24 的测量报告；[首轮 CI](https://github.com/yao1145/ReactiveMD/actions/runs/39782886373) 已通过并生成报告。

## 宿主中的大文档

文档源码上限为 1,000,000 个 UTF-16 代码单元，绘图和表达式还有独立计算预算，详见[安全策略](../../SECURITY-ch.md)。资源上限控制工作量，编译 API 仍是同步调用。编辑器可以合并连续输入触发的编译；处理来源不可信或较大的文档时，可以在宿主 Worker 或独立进程中编译，并由宿主控制并发和超时。

语法节点预算默认 10,000，宿主可用 `compileLocal(source, { limits: { maxSyntaxNodes: 50_000 } })` 按次调整，见[核心 API](../integration/local-integration-ch.md#核心-api)。提高预算后应同时测量编译、内存和最终预览渲染成本。

## 渲染优化契约

参考渲染器使用编译器产出的依赖信息，跳过不可能读取已变化参数的子树。这是内部渲染优化，不是作者可见功能，也不是新的公开 API。

- 公开契约是语义等价：状态值、渲染文字、诊断、可访问属性、静态 SSR 输出和交互行为与不做条件渲染时一致，只有重新计算的范围变化。
- `document.dependencies` 是冻结、可序列化的内部映射。无法静态判断读取范围的子树标记为 `null`，对这些子树保守渲染。宿主和其他渲染器不得依赖其结构，可以完全忽略。
- 源码变化、实例销毁、面板重置，以及可能改变隐藏状态的可见性变化，仍会更新受影响的子树。优化不会抑制诊断或校验提示。
- `npm run verify:memo` 在相同文档和状态修订上比较优化渲染与无条件基线；`npm run verify:release` 包含该检查。只有两者产生等价的可观察输出，渲染优化才可接受。

## Playground 实时编辑

Playground 在独立的模块 Worker 中调用公开的 `compileLocal`，将连续 150 ms 内的编辑合并。调度器最多保留一个正在编译的任务和一份最新待编译源码；过期结果不会替换当前预览或诊断。输入框和导出始终使用最新源码，等待编译时显示“编译中”并保留上一次预览。预览组件复用相同文档，避免每次按键重建整个预览。

源码保存延后执行，切换示例或离开页面时保存待写入的内容。Worker 无法使用或运行失败时，页面提示降级，并合并编辑后在主线程编译；该模式仍有大文档阻塞的成本。正常 Worker 模式中，接收编译结果后的 React 渲染、排版与绘制仍在主线程执行。

语言包的同步编译 API 和 `LocalReactiveDocument` 保持原有行为。其他宿主可以参考 `demo/src/local-compile-worker.ts` 与调度器，将编译放到自己管理的 Worker。

### 复测

在仓库根目录构建语言包后执行：

```sh
node scripts/benchmark-large-documents.mjs
```

脚本预热 3 次、测量 20 次，检查 10、100、300、600 节文章编译结果并保存中位数和 P95。启动 Playground 后，可以从仓库根目录执行以下浏览器检查；默认服务器为 `http://127.0.0.1:5184`，可用 `DEMO_URL` 覆盖。

```sh
node demo/scripts/verify-editing.mjs
node demo/scripts/benchmark-editing.mjs
```

编辑基准在 300 节、约 47,000 字符的文章末尾连续键入 10 个字符，按键间隔为 20 ms，记录输入事件到下一次 `requestAnimationFrame` 回调的延迟和主线程长任务。该指标用于观察输入响应，不等同于画面完成绘制的时间；长任务统计包含最终预览渲染。`EDITING_SECTIONS` 可调整节数，`EDITING_REPORT` 可指定报告路径。所有报告写入忽略目录 `artifacts/`。

2026-10-22，在上述 Windows 机器上用本机 Edge 对同一份 46,969 字符文章进行一次前后对比。两边均使用 Vite 开发服务、1440 × 1000 视口，原版为 `94fd72e`，优化版包含本节描述的 Worker 调度与预览复用。

| 指标 | 原版 | 优化版 |
| --- | ---: | ---: |
| 输入到下一帧回调的中位延迟 | 147.3 ms | 9.5 ms |
| 输入到下一帧回调的最大延迟 | 157.9 ms | 36.9 ms |
| 连续键入 10 个字符的总耗时 | 2,302 ms | 538 ms |

原始报告分别为 `artifacts/benchmark-editing-before.json` 和 `artifacts/benchmark-editing-after.json`。这是一次本机观测，机器负载会影响数值。优化主要减少按键触发的主线程工作，同步 `compileLocal` 本身的算法和单次编译速度保持原样。
